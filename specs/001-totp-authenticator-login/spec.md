# Spec 001: Authenticator (TOTP) Setup on First Login

## 1. What & Why
Replace the email-dependent 4-digit OTP delivery flow on `/admin/login` with an **RFC 6238 Authenticator (TOTP — Microsoft Authenticator / Google Authenticator) enrollment on first login** and **Authenticator code verification on subsequent logins**, while also allowing the Superadmin (`boris@computacionintegral.com`) to view/deliver live access codes or Authenticator setup credentials for client accounts without email (`test@sperling`).

## 2. Root Cause Analysis
- **Root Cause 1 (No SMTP Transport):** `generateFourDigitToken()` in `cms/auth/tokens.ts` generated a 4-digit code and logged a masked message to stdout, but no SMTP server or transactional email provider is configured in the environment. Consequently, `boris@computacionintegral.com` never received the 4-digit code in his inbox and could not complete login.
- **Root Cause 2 (Stateless Serverless Persistence):** Vercel serverless functions do not share memory across invocations, so per-user TOTP secrets and enrollment states must be derived deterministically via HMAC-SHA256 using `PAYLOAD_SECRET` + user identity, paired with signed HTTP-only cookies for device enrollment state and session persistence.

## 3. Functional Requirements
- **FR-001 (Deterministic RFC 6238 TOTP Engine):** Implement standard RFC 6238 TOTP (HMAC-SHA1, Base32 secret derived deterministically per user from server secret, 30-second period, ±1 step window tolerance for clock drift) compatible with Microsoft Authenticator and Google Authenticator.
- **FR-002 (First-Login Authenticator Enrollment):** When an authorized user (`boris@computacionintegral.com` or `test@sperling`) initiates login and does not yet have an active enrollment cookie (`infusio_totp_enrolled_<userId>`)—or explicitly requests setup—return the `otpauth://` URI, scannable inline SVG QR code, and Base32 manual setup key so they can pair Microsoft Authenticator immediately and verify their first 6-digit code.
- **FR-003 (Subsequent Login Verification):** When an already-enrolled user enters their identifier (or toggles to direct code entry), prompt solely for the 6-digit code from Microsoft Authenticator without exposing the QR/secret unless re-setup is requested.
- **FR-004 (Backup 10-Minute Admin Dispatch Code for Client):** Support both the client's 6-digit Authenticator TOTP code AND an admin-generated 10-minute code so `boris@computacionintegral.com` can either provide `test@sperling` with a live code or their Authenticator setup key from `AdminDashboard.tsx`.
- **FR-005 (Zero Credential Leakage on Login UI):** Keep `/admin/login` strictly free of example usernames, emails, or tokens in placeholders, while maintaining the exact `infusio-site` visual design.

## 4. Acceptance Criteria
- **AC-1:** Entering `boris@computacionintegral.com` on `/admin/login` on first login displays a scannable QR code (inline SVG) and manual Base32 secret key for Microsoft Authenticator (`otpauth://totp/Infusio%20CMS:boris%40computacionintegral.com?...`).
- **AC-2:** Submitting a valid 6-digit TOTP code generated by the RFC 6238 algorithm for `boris@computacionintegral.com` authenticates the session (`HTTP 200`), sets `infusio_auth_token` and `infusio_totp_enrolled_usr_admin_boris` cookies, and redirects to `/admin`.
- **AC-3:** Once enrolled (`infusio_totp_enrolled_<userId>` cookie present), `POST /api/auth/request-code` returns `firstLogin: false` and `/admin/login` goes directly to the 6-digit Authenticator code input without exposing the QR code.
- **AC-4:** Superadmin dashboard (`AdminDashboard.tsx`) displays live TOTP code + Authenticator setup key / 10-minute dispatch option for `test@sperling`, and `test@sperling` can log in to the scoped Camp David MVP dashboard.
- **AC-5:** Login page contains zero example emails or tokens in placeholders, and `npm run type-check` + `npm run build` pass with 0 errors.
